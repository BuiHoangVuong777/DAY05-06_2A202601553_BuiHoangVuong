## 1. Chunking strategy — semantic, not fixed-size

One chunk = one unit the author already wrote as a self-contained topic. No token windows, no overlap, no splitting mid-list.

| Source shape | Unit → chunk | Files |
|---|---|---|
| `timeline[]` | one chunk per program week | `master_timeline.json` |
| `operating_notes[]`, `note` | one chunk per note | `master_timeline.json` |
| `chunks[]` (author-provided) | used as-is | `cohort3_evening_calendar.json` |
| `events[]` | one chunk per event | `cohort3_evening_calendar.json` |
| `blocks[]` | one chunk per block | runbook, discord, xp, quality-control |
| `sections[]` | one chunk per section | `cohort3_team_and_topic_selection.json` |
| `documents[] → sections[]` | one chunk per nested section | `cohort3_knowledge_base.json` |

Why blocks rather than individual lines: a block like *Cách kiếm XP* is six scoring rules that are only meaningful together — a query like *"kiếm XP bằng cách nào"* wants all six. Splitting per line would strand `/daily → +5 XP` without its context; merging a whole file would blur XP rules into level thresholds. Largest chunk is the 16-item workshop curriculum, kept whole because it is queried as one list.

`content` is plain text, one source item per line. Object items use a fixed template per shape so **no source field is silently dropped**:

| Source shape | Rendered as |
|---|---|
| `{command, description}` | `/daily — Nộp daily stand-up` |
| `{level, name, threshold_xp}` | `LV1 — Active Builder — ngưỡng 200 XP` |
| `{order, title, detail}` | `8. RAG Pipeline — Ingestion, chunking, retrieval` |
| `{title, importance, detail, reason}` | `[Cực kỳ quan trọng] AI Log: … Lý do: …` |
| any unrecognised object | every non-empty key rendered `k: v`, sorted |

## 2. Deduplication

`cohort3_knowledge_base.json` is an **aggregate**: it restates `master_timeline.json`, `cohort3_weekly_runbook.json` and `cohort3_team_and_topic_selection.json` in condensed form, and adds one genuinely unique document (`support_system`). All 12 removals are aggregate chunks losing to their standalone original.

- **4 exact** (`hash` collision after NFC + whitespace normalization).
- **8 near** (token Jaccard ≥ 0.65), e.g. *"Mỗi đề tài tối đa 2 teams."* vs *"Mỗi đề tài tối đa 2 teams / đề tài."*

**Canonical beats recent, deliberately.** The aggregate file has a *newer* mtime than the standalone files, but it is a strictly lossier restatement — it drops week date ranges, `gate` labels, curriculum `order`/`detail` separation, and the 25/07 deadline metadata. Ranking is `canonical → priority → longer content → newer mtime → id`; the last key makes ties total, so the winner never depends on iteration order.

**Threshold is evidence-based, not guessed.** At 0.75 one true duplicate (knowledge-base week 3 vs timeline week 3, which reworded *"Bắt tay vào code"* → *"Bắt đầu code"*) scored 0.6842 and survived. The report showed it was the *only* pair anywhere between 0.35 and 1.0, so lowering to **0.65** captured it with nothing else nearby. `near_misses_below_threshold` is now empty — clean separation. **Re-check that list if the corpus grows**; a bigger corpus may put unrelated pairs in the 0.65-0.75 band.

Result: `cohort3_knowledge_base.json` contributes 2 chunks (its unique `support_system` sections) instead of 14.

## 4. Fields that are derived, not authored — read before you trust them

- **`created_at` / `updated_at` are filesystem mtimes.** No source file carries any timestamp. They are real and traceable but are **not** authorship dates, and a fresh `git clone` will reset them. Use for recency tie-breaks only; re-run the script after operations that rewrite mtimes.
- **`version` is the schema/pipeline version (`1.0.0`), not a document version.** No source declares one. Bump it when the record shape or rendering rules change.
- **`priority` scales differ per file and are not globally comparable.** `master_timeline.json` uses 1-6 as *week ordinals* (week 6 = priority 6, the most important milestone); other files use 1-2 as *importance* (1 = highest). Compare only within a single `source_file`, or you will rank Demo Day last.
- **`status`** is grounded where a source states one (`Đã xong`→`completed`, `Hiện tại`→`active`, `Upcoming`→`upcoming`); everything else defaults to `active`. Current split: 31 active / 4 upcoming / 1 completed.
- **`summary` is extractive**, never model-generated — first 1-2 sentences (prose) or first 2 lines joined with `; ` (lists). It therefore cannot assert anything the chunk does not already say.

Time-of-day questions are **unanswerable** from this corpus; don't let an agent guess.

## 6. Ingesting

Embed a composed string, not `content` alone — the titles carry retrieval signal that bare content lacks:

```
{title}\n{section}\n{summary}\n{content}
```

Store the remaining fields as filterable metadata. Recommended filters: `status in (active, upcoming)` for "what's happening now", `week` for phase questions, `event_type` for calendar questions, `cohort` when cohort 4 data is added (note the 11 nulls above).

`hash` supports incremental upsert: key on `id`, skip when the stored `hash` matches. `id` is stable across content edits (it derives from file + JSON pointer), so an edited chunk updates in place rather than orphaning the old vector.

**Traceability.** Every chunk reconstructs to its exact origin:

```bash
jq '<source_pointer>' <source_path>      # e.g. jq '/timeline/1' -- see note below
python3 -c "import json;d=json.load(open('codebase/data/rag/master_timeline.json'));print(d['timeline'][1])"
```

`source_pointer` is an RFC 6901 JSON Pointer (`/timeline/1`, `/documents/3/sections/0`); `jq` needs it as `.timeline[1]`, so convert or use the Python form above.

## 7. Determinism

Verified: two consecutive runs produce a byte-identical `rag_chunks.jsonl` (sha256 `08e975cb48f2bf86…`). Guaranteed by sorted file iteration, sorted output, a total ordering key in dedup, NFC normalization before hashing, and no clock or randomness anywhere in `id`, `hash`, or record order.

`rag_dedup_report.json` is likewise timestamp-free. The only non-deterministic inputs are the filesystem mtimes that populate `created_at`/`updated_at`.
