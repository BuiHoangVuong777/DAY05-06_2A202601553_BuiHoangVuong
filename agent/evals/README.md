# Agent eval suite

36 cases over the agent, the SSOT, and the RAG policy corpus. `cases.json` is the
spec; `run_evals.py` holds one implementation per `eval_id`. **The runner exits 2
if the two drift apart**, so a case can never be documented without being executed.

```bash
export SSOT_DB_PATH=./ssot/ssot.db
export RAG_BASE_URL=http://localhost:8000

python3 -m agent.evals.run_evals                    # run all
python3 -m agent.evals.run_evals --only EV-PRIO     # prefix filter
python3 -m agent.evals.run_evals --json report.json # machine-readable report
python3 -m agent.evals.run_evals --refresh-snapshot # after FORCE_RESEED=1
```

Exit `0` all clear · `1` a blocker/major case failed · `2` spec/impl drift.
`SKIP` never fails the run — a dependency being down is not an agent defect.

| File | |
|---|---|
| `cases.json` | case metadata: behavior, severity, determinism class, coverage gaps |
| `run_evals.py` | implementations + runner |
| `snapshot.json` | pinned expectations for the 6 snapshot-bound cases |

This complements `agent/test_agent.py` (19 unit tests on rules and schema). The
evals additionally cover SSOT integrity, policy grounding against the real corpus,
negative paths, and write safety.

## Two determinism classes

`seed.sql` computes deadlines **relative to seed time**, so absolute timestamps
change on every re-seed.

- **invariant** (30 cases) — hold after any re-seed. Assert predicates and
  relationships: *every overdue alert is past due*, *the milestone boost is
  exactly 120 points*.
- **snapshot** (6 cases) — pinned to `snapshot.json`. After `FORCE_RESEED=1`,
  run `--refresh-snapshot`; drift there is expected, not a defect.

## The SSOT is synthetic

Generated by `ssot/seed.sql`. Users, projects, tasks and blockers are fixtures —
all 5 teams carry identical load, all 15 blocked tasks share one blocker string.
These cases validate **agent mechanics**, not real team progress. Re-point
`SSOT_DB_PATH` at the production database and re-derive the snapshot before
treating results as operational. The runner prints this banner on every run.

## Known failing case

**`EV-NEG-004` — conflicting policy is not surfaced.** The corpus contains two
irreconcilable Demo Day dates:

| Source | Claim |
|---|---|
| `cohort3_evening_calendar.json/chunks/1` | 03/09, 04/09, 05/09/2026 |
| `master_timeline.json/timeline/5` | Week 6 = 01/09/2026 |

Both are **retrieved** (the timeline chunk ranks 3rd at 0.6854), and the system
prompt already instructs the model to flag contradictions — but the answer states
only the calendar dates with no mention of the conflict. This is a real quality
gap, left failing on purpose rather than asserted away. Fixing it means
strengthening the disclosure instruction or adding a conflict-detection step;
either is a change to the RAG prompt, not to this suite. The underlying data
defect is documented in `output/rag_ingestion_notes.md` §3.

## Bug this suite already caught

`EV-DAILY-004` and `EV-DUESOON-001` failed on first run: the agent compared
SSOT timestamps (UTC, from SQLite `datetime('now')`) against `datetime.now()`
(host local). On this UTC+7 host every "due today" row was rejected as off-date
and the due-soon window was shifted 7 hours. Fixed by `priority.utc_now()`, now
used by `agent.run()` and `priority.rank()`.

## Adding a case

1. Append an entry to `cases.json` with an `eval_id`, `severity`, `determinism`
   and `source`.
2. Add `def ev_<id>() -> (status, detail)` in `run_evals.py` and register it in
   `REGISTRY`.
3. Run — the drift guard fails if you did only one of the two.
